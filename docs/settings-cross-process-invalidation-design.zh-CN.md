# 设置读取与跨进程失效：P1 前置设计（未实现）

本文件只给出方案，不引入缓存、存储键、默认值、数据库版本或 IPC 变更。当前同步读取仍是事实源。

## 现状与边界

- `DataStore.configurationStore` 包装 `PublicDatabase.kvPairDao`；数据库持久化，使用 TRUNCATE journal，并已启用 Room `enableMultiInstanceInvalidation()`。当前 `RoomPreferenceDataStore.get*` 每次查询 DAO。
- `RoomPreferenceDataStore` 的 `fireChangeListener` 是本进程 Kotlin 回调。另一个进程写表不会调用本进程的这个 listener；Room 的表级失效不等于此 listener，更不等于自建 Map 已刷新。
- `DataStore.profileCacheStore` 来自 `TempDatabase` 的内存数据库，各进程独立，不能把它当作跨进程共享设置源。
- Manifest 的 `:bg` 服务与 UI 进程都可访问配置；后台可写当前 profile、运行状态相关配置，UI 可写选择、外观和代理参数。订阅/恢复等批处理也会修改数据。Root 模块进程不能直接读这个 Android 私有 Room 库；模块配置及状态文件属于另一条协议，不纳入本缓存。
- `ProfileListPrefs` 是页面恢复时在 IO 读取的少量显示参数快照，仅用于卡片绑定；它不是通用设置缓存或跨进程一致性承诺。

## 候选协议（单独批准后才实施）

1. 在同一个 PublicDatabase 事务内写目标键，并递增独立配置代数；删除、reset、批量恢复同样递增。代数元数据不能借用现有用户设置键，届时需独立 schema 方案与迁移评审。
2. 每个进程建立表级 `InvalidationTracker.Observer`，失效通知只将本进程快照标记为 dirty，不在回调中逐键同步查询，不猜测哪一个键变了。Room 多实例通知负责唤醒，不作为唯一正确性依据。
3. IO 线程在同一读事务中读取代数和所需键，形成不可变快照；完成后在互斥保护下一次替换。重叠读取只能安装较新代数，禁止较旧结果覆盖新值。
4. 所有写入口必须经同一事务封装；本进程写提交后也标 dirty。DAO 直写、reset、批量恢复若未纳入，不允许启用缓存。UI 仅从 StateFlow 接收完整快照，不进行逐键数据库读取。
5. 首次访问、进程恢复/重连、数据库替换及备份恢复后强制重新获取代数和快照；清空内存值。不能依靠进程一直存活或广播一定送达。
6. 丢失通知通过生命周期恢复时的代数校验兜底；代理启动、配置生成、节点切换等要求当前值的动作在 IO 上事务读取，不凭可能过期的显示缓存执行。
7. DB 锁定/损坏、IPC 重连或读取异常时保留上一次快照但标为 stale；关键动作拒绝用 stale 值继续，显示层可保留旧值并提示。读取失败不能写回默认值覆盖数据库。

## 取舍与验收

表级 dirty 可能导致多余刷新，但比不完整的键级广播可靠。先完成读写入口盘点与 StrictMode/Perfetto 基线，再决定值得缓存的键；不要为降低查询次数引入全局无界 Map。当前不改变 journal 模式，不将 WAL 当成缓存一致性协议。

实施前必须具备以下自动化与设备验证：

- UI 写 / `:bg` 读、反向写读、两进程并发、同一键冲突（按数据库事务提交顺序）、多键事务一致快照。
- 通知丢失或重复、快照读取中途新写、旧读取晚返回、进程被杀重启、Room invalidation 服务重连。
- remove/reset/恢复导入、空值与默认值、数据库替换及升级、不改变现有设置键语义。
- 后台写入后 UI 恢复可见、关键代理动作读取新值；StrictMode 不报告新增主线程磁盘访问。
- 比较查询次数、卡顿、内存与刷新延迟；无实测收益则不启用缓存。保留可独立回滚路径。

结论：本轮仅提交设计。跨进程失效、代数 schema 与缓存代码均未实现；既有 Room 多实例失效本身不足以批准通用缓存。
